# AI Agent/MAS Access Control 연구 Need 조사 개요

**기준일: 2026-11-23.** 이 문서는 연구 방향을 정하는 제안서가 아니라, 정책 **생성(Generation) → 집행(Enforcement) → 정확성 검증(Verification/Correctness)** 사이에서 기존 해결책과 남은 조건을 연결한 문헌조사의 결론이다. 세 관점은 겹친다. 정책 생성이 올바르더라도 집행 위치가 다르면 효과가 달라지고, 형식적으로 검증한 집행도 잘못 생성된 정책을 올바른 사용자 승인으로 만들지는 못한다. 상세 근거·서지 정보는 [연결 연구 지도](linked_research_map.md), [한계·대응 비교표](limitation_resolution_matrix.md), [개별 Need 평가](research_need_assessment.md)에 있다. 수치와 실패 사례는 모두 **논문 저자의 보고**이며 이번 조사에서 실험을 실행하지 않았다.

## 조사 범위와 증거 읽는 법

- 연결 연구 시트 [261018_Controllable_Agent](https://docs.google.com/spreadsheets/d/1abFjTBcpDAYTZFAVOTUtYH28jKw3xhKg6JCjCGX5Tjg/edit?gid=1753709696)를 **읽기 전용**으로 열었다. `Overview`의 A1:Z80·A200:Z310·A311:Z480과 `Related_works`의 A1:Z220·A221:Z500을 확인했다. `Overview` 233행 이후의 세 범주 비교는 탐색 출발점으로 사용했다. **두 탭 전체를 완독한 것으로 간주하지 않으며**, 서지·주장·평가 수치는 가능한 한 논문 원문과 공식 문서로 재검증했다. 기존 저장소 자료도 배경으로만 사용했다.
- 근거 등급은 **A** 저자 명시 한계, **B** 원문 메커니즘·평가 범위에서 직접 확인한 제한, **C** 연구자 추론, **D** 논문 내 시험·반례에서 관측된 실패다. D는 해당 환경의 관측이지 다른 연구·배포의 일반 실패를 뜻하지 않는다. `PARTIALLY_RESOLVED`는 조건부 해법과 잔여 조건이 모두 있다는 뜻이고, `UNVERIFIED`는 기존 방법을 대조한 뒤에도 해결 불가하다는 근거가 아직 부족하다는 뜻이다.
- 출판 상태를 구분했다. [Conseca](https://doi.org/10.1145/3713082.3730378)는 HotOS 2025, [DRIFT](https://doi.org/10.52202/085713-2791)는 NeurIPS 2025, [ControlValve](https://openreview.net/pdf?id=PNU9Rj5RDQ)는 ICLR 2026, [AgentBound의 MCP 격리 연구](https://doi.org/10.1145/3808103)는 ACM FSE 2026, [SkillScope](https://doi.org/10.1145/3830454.3846588)는 ACM CCS 2026이다. [Cedar](https://doi.org/10.1145/3649835)는 OOPSLA 2024, [Margrave](https://doi.org/10.1145/1062455.1062502)는 ICSE 2005, [ZELKOVA](https://doi.org/10.23919/FMCAD.2018.8602994)는 FMCAD 2018로 검증했다. 아래에서 arXiv 버전만 명시한 2026년 연구는 별도 심사 출판을 확인하지 못한 **프리프린트**다. DOI·전체 저자·원문 버전은 연결 지도 서지표에 기록했다. NVIDIA OpenShell v0.1.9는 논문이 아닌 [공식 제품 문서](https://docs.nvidia.com/openshell/v0.1.9/how-it-works/policies/overview)로 다룬다.

## 세 관점의 발전 흐름

### 1. Policy Generation: 작업 범위에서 출처·동적 값·위임으로

**사전 정책과 동적 작업.** Conseca는 공격자 작성 내용을 정책 생성기에 주지 않고 trusted context·사용자 요청·도구 설명으로 작업별 도구/인자 규칙을 만든다([§§2–3](https://arxiv.org/pdf/2501.17070v3)). 저자는 이 때문에 작업 중 발견한 관리자 메일 같은 자료에 의존하는 행위를 미리 예상하기 어렵다고 명시한다(**A**, §3.3). DRIFT는 이탈한 실행 경로의 Read를 허용하고 Write/Execute는 LLM validator로 사용자 의도와 대조해 추가하며, 삽입 지시는 isolator가 가린다([§§3.1–3.3](https://arxiv.org/pdf/2506.12104v3)). 이는 동적 재계획을 **부분적으로** 다루지만 확대 판단은 validator의 의미 판정에 의존한다(**B**). DRIFT의 NeurIPS 2025 논문과 [arXiv v3 §4](https://arxiv.org/pdf/2506.12104v3)의 2026년 추가 AgentDyn 평가는 같은 시점의 학회 결과로 섞지 않았다. Progent v3는 갱신된 허용 집합의 포함관계를 SMT로 확인해 **승인 없는 확대를 막는다**([§§4.3, 6](https://arxiv.org/html/2504.11703)); 최초 정책이나 승인 결정의 의미까지 증명하지는 않는다. 저자의 §8.1 기본 평가가 확대를 자동 승인하며, §8.2의 Manual Approval ASR 0%는 [Appendix D](https://arxiv.org/pdf/2504.11703v3)의 보안에 밝은 사용자 가정 아래 얻었다. 여기서 Progent의 갱신 검사를 빼고 “동적 정책 확대는 전혀 통제되지 않는다”고 쓰는 것은 틀리다.

**정확한 인자와 값의 출처.** PAuth는 user-signed task를 서버별 natural-language slice로 변환하고 authoritative 서버의 값·계산 계보를 signed envelope로 묶어 실제 operator/operand를 서버에서 검사한다([§§III–IV](https://arxiv.org/pdf/2603.17170v2)). 저자의 [§V Table III](https://arxiv.org/pdf/2603.17170v2)에서는 명확하게 보완된 task 100/100이 추가 확인 없이 통과했지만 원래 AgentDojo task는 71/100만 그랬고, 634/634 off-task **호출 변형**은 확인 절차로 보냈다. 이 수치를 장기 agent 전체 궤적의 634건 차단으로 바꾸지 않는다. PAuth는 자기완결적이고 모호하지 않은 task, 올바른 서버 측 번역과 authoritative 값의 진실성을 신뢰한다([§§II–III, V–VI](https://arxiv.org/pdf/2603.17170v2)). PACT의 인자 역할별 provenance 계약([§3](https://arxiv.org/pdf/2605.11039v1)), ROPE의 user-named source/record와 값 검증([§§2–3](https://arxiv.org/pdf/2608.27496v2)), IntentCap의 필드별 권위 분리([§2](https://arxiv.org/html/2609.14631)), CXI의 protected sink field용 trusted release([§§2–3](https://arxiv.org/pdf/2607.06000v1))는 “외부 데이터에서 나온 인자는 모두 무방비”라는 주장을 반박한다.

**출처가 맞아도 값의 의미는 별개.** ROPE는 사용자가 수취인 선택을 공격자 쓰기 가능한 청구서 전체에 위임했을 때, 안전한 수취인과 공격자 수취인을 출처만으로 구분하지 못한 평가 사례를 보고한다(**D**: 공격 성공 7건; 정상 위임 관련 거부 83건, [§5 Tables 4–5](https://arxiv.org/pdf/2608.27496v2)). [SPILLWAY §§2–3, §5 Tables 2–3](https://arxiv.org/pdf/2611.07222v3)는 typed identity field와 고정 delegation rule, sanitized judge로 일부 간접 대상을 회복하며 2,847개 평가 attack pair의 in-scope target 성공 0을 보고한다. **단**, typed field 직접 오염은 위협 모델 밖이고 ROPE의 동일 7건·83건을 전부 재평가한 결과는 아니다(**A/B**, §2·§7). PAuth의 signed value도 *그 값에 권위가 있는 서버*라는 가정에 상대적이므로 임의 청구서 free text의 의미적 참값을 자동 판별했다고 해석하지 않는다. 따라서 이 문제는 **조건부 해결**이고, 더 넓은 일반성은 `UNVERIFIED`다.

**MAS의 하위 작업.** ControlValve는 내부 tool call을 볼 수 없는 서브에이전트 환경에서 사용자 작업과 사용 가능한 agent로 CFG·agent-edge 규칙을 만들고 호출 순서/메시지를 검사한다([§4 Fig. 4](https://openreview.net/pdf?id=PNU9Rj5RDQ)). 저자 평가의 비적대적 `INTERNAL ONLY` 문서 외부 메일 포함은 56%에서 13%로 줄었지만 0이 아니었다(**D**, [§6.6](https://openreview.net/pdf?id=PNU9Rj5RDQ)). [*From Procedures to Permissions* §3–4 Table 2](https://arxiv.org/pdf/2611.08905v1)는 Skill/SOP에서 서브에이전트 권한을 학습하는 다른 접근이며, 이것만으로 실행 경계의 강제 보장을 얻는 것은 아니다. [ACaM §§3–7](https://arxiv.org/pdf/2611.23507v1)은 white-box Python tool 코드에서 설명과 실제 capability의 차이를 분석한다. 따라서 “MAS 정책 생성 연구 부재”는 성립하지 않는다. 생성된 CFG·권한 목록의 의미 정확성 및 실제 service effect와의 연결은 별도 조건이다.

### 2. Policy Enforcement: 호출 → 실행 이력·정보흐름 → OS·서비스 효과

**Tool/trace 경계.** Progent는 tool name·인자 정책을 호출 직전에 검사한다([§§4–5](https://arxiv.org/html/2504.11703)). FORGE/SASY는 trusted instrumentation의 event history와 provenance를 Datalog 정책에 넣고 tool dispatch·HTTP join point에서 검사한다([§§3–4](https://arxiv.org/html/2602.16708)). FORGE의 [§5 Table 4](https://arxiv.org/html/2602.16708)는 지정 provenance 정책에서 AgentDojo effect ASR 0.2±0.12%, 무공격 utility 62.5±1.4%를 보고한다. 그러나 §7.1은 raw socket/direct stdio·메서드 내부 동시성 같은 비계측 경로를 명시한다(**A**). 이를 tool 계층 자체의 한계로 좁혀 읽어야 한다. ActPlane의 kernel hook, OpenShell의 Landlock/proxy/OPA, AgentBound의 MCP 서버 container는 다른 집행 경계를 제공한다([ActPlane §§2–3](https://arxiv.org/html/2606.25189), [OpenShell overview](https://docs.nvidia.com/openshell/v0.1.9/how-it-works/policies/overview), [AgentBound §§2–3](https://arxiv.org/html/2510.21236)). OpenShell의 L7 `audit`는 허용 후 기록이고 `enforce`가 차단이라는 [공식 설정 설명](https://docs.nvidia.com/openshell/v0.1.9/security/best-practices)도 중요한 집행 조건이다. 하위 경계가 API 인자의 업무 의미를 아는지는 다시 서비스 측 정책과 비교해야 한다.

**Agent 간 출처와 위임.** Multi-CaMeL은 각각 안전한 단일 agent를 연결해도 SQL 결과가 child의 trusted instruction으로 승격되는 boundary laundering 사례를 제시하고(**D**, [§III](https://arxiv.org/html/2610.05640)), `message`와 `variables`를 분리하며 capability/provenance를 전달한다([§IV](https://arxiv.org/html/2610.05640)). [§V Table III](https://arxiv.org/html/2610.05640)의 multi-agent 평균 공격 성공 0%는 fresh child·tree delegation과 **비자명한 인가 정책을 사용하지 않은** 시험 범위에 한정된다(§II·§VI, **A/B**). [LLMbda §§1–5](https://arxiv.org/html/2602.20064)와 [FIDES §§3–5](https://arxiv.org/html/2505.23643)는 implicit flow·IFC의 별도 대안이다. A2A에서는 현재 caller 인증과 최초 사용자 승인/각 hop의 권한 축소가 다르다. [Donno et al. §V-A–B](https://arxiv.org/html/2611.07050)는 공유 HMAC 키를 가진 중간 agent가 origin authority evidence를 다시 만드는 시험 사례를 보고한다(**D**). 이것은 그 키 설계의 제한이며 서명된 origin grant, token exchange, [SAGA §§IV-D/E](https://www.ndss-symposium.org/wp-content/uploads/2026-s869-paper.pdf) 등 다른 접근의 일반 실패는 아니다.

**Provider effect와 비동기 철회.** 도구 호출이 허용되어도 검토한 대상의 버전이나 이미 수용된 provider 작업이 뒤에 바뀔 수 있다. [EffectBound §V-B Table III](https://arxiv.org/html/2609.02866)는 GitHub MCP 경로에서 reviewed head 변경 뒤 다른 head를 merge한 25/25 사례와, native API의 SHA 결속을 사용한 0/25 사례를 함께 보고한다(**D**, 해당 경로). §V-C의 Kafka 4.3.1 시험은 철회 뒤 기존 ProduceRequest append를 관측하고 effect fence로 막았다(**D**). [CTA §§2–4](https://arxiv.org/pdf/2607.10487v2)와 [CONTINUITY §§5–6](https://arxiv.org/html/2609.05269)는 선언된 현재 정책·정확한 효과를 commit/finality에서 재검사한다. [Authorization Revocation §§2–5, §8](https://arxiv.org/html/2609.21284)은 queue/callback/provider carrier를 포함한 root cut·fence·quiescence를 정의하고 provider-free 17-case suite에서 시험했다. 이는 신규 credential 거절을 다루는 [HBHC §§3–4](https://arxiv.org/html/2605.20704)와 다른 목표다. **이미 알려진 native precondition·원자적 검사·fence라는 해결 경로가 있으므로**, 특정 MCP 표면의 미결속을 전체 agent 보안의 새로운 불가능성으로 확대하지 않는다. 실제 provider 경로 목록·동시성·fence 내구성은 제품별로 확인해야 한다(**A/B**: [EffectBound §VI](https://arxiv.org/html/2609.02866), [Authorization Revocation §10.2 Table 7](https://arxiv.org/html/2609.21284)).

### 3. Policy Verification/Correctness: 정책 *형식*, 승인 *의미*, 실제 *집행*

**형식 정확성.** Margrave의 XACML 변경 영향, ZELKOVA의 IAM SMT, Cedar의 schema·정책 동치/포함·반례는 이 문제의 견고한 선행 해법이다([Margrave §1–3](https://web.cs.wpi.edu/~kfisler/Pubs/icse05.pdf), [ZELKOVA §§I–IV](https://kasperluckow.com/papers/fmcad2018.pdf), [Cedar §§2.5–2.6, 4.4](https://arxiv.org/html/2403.04651)). [AWS AgentCore Policy 생성 검증 문서](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-generation-validation.html)는 Cedar 검증과 `ALLOW_ALL` 같은 넓은 결과의 점검을 실제 서비스에 제공한다. 따라서 **형식 검증 자체를 미개척 Need로 재포장할 근거가 없다**. [Cedar 개발 검증 §§3–4](https://arxiv.org/html/2407.01688)의 Lean 모델과 Rust 구현 검증도 “전체 구현이 기계 증명되었다”는 뜻으로 확대하지 않는다.

**승인 의미의 정확성.** 자동 생성 후 형식 검증만으로는 원문 사용자 요청 또는 조직 정책에 없는 허용·금지를 발견할 수 없다. FORGE는 자연어→Datalog 번역의 누락/조건 오해를 인정하며, 구성 trace에서 judge와 일치한 정책이 held-out 정상 취소를 잘못 막은 Task 43을 보고한다(**A/D**, [§3.4, Appendix H.1/H.3 Table 9](https://arxiv.org/html/2602.16708)). [Text2NGAC §5.2 Table 15](https://arxiv.org/html/2611.12572)의 상위 자원 추상화 변이는 구조 검사에서 11/120만 탐지됐지만 보완 review routing은 114/120을 flag했다(**D**). 후속 [NGAC-IR §§3–6 Table 3](https://arxiv.org/html/2611.26941)은 원문 문장과의 역번역으로 평가된 오류 31개 중 26개를 검출했으나 조건 누락 등 5개는 놓쳤다(**D**). [AutoCedar §§III, V-D Table VI](https://arxiv.org/html/2607.03656)는 검토된 target과 정책의 정형 일치를 제공하지만, target을 통과한 197개 중 19개는 독립 gold와 어긋났다(**D**). 독립적으로 올바른 target이 있고 사용자가 이를 승인하면 이들 방법이 강한 해법이다. 따라서 “의미 정합성이 전혀 연구되지 않았다”도, “검증된 정책은 곧 사용자 의도와 같다”도 성립하지 않는다.

**집행 정확성.** [AuthGraph §§3–5](https://arxiv.org/html/2605.26497)는 사전 승인 graph와 실행 graph를 비교한다. [FAVA Method/RQ5 Fig. 5](https://arxiv.org/html/2607.27267)는 evidence graph·SMT·gateway를 쓰면서도 한 저장소의 test/export obligation이 IR에서 빠져 허용된 평가 사례를 보고한다(**D**). [Agentproof §§5–7, 9](https://arxiv.org/html/2603.20356)는 workflow graph의 구조·시간 속성을 다루지만 LLM 출력의 의미는 증명하지 않는다(**A**). [Temporal Runtime Verification §§1, 3–5](https://arxiv.org/html/2610.09793)는 로그에 대한 **오프라인** 평가이며 실시간 차단 결과가 아니다. 반대로 [ASU §§5–7](https://arxiv.org/html/2610.21063)는 신뢰 경로에서 보여 준 정확한 effect descriptor와 서명된 승인을 gateway의 동일 실행에 결속한다. [OpenShell Policy Prover](https://docs.nvidia.com/openshell/v0.1.9/how-it-works/policies/prover)의 SMT pass는 지정한 containment에 대한 것이며 실제 작업의 최소권한·서비스 효과의 증명은 아니다. 이 범주의 정리는 항상 **검증한 정책·신뢰한 증거·매개한 효과**에 상대적이다.

## 반복되는 전제와 반박해야 할 잔여 질문

|---|---|
| 사용자 승인과 조직 정책이 명확하고 정당하게 구조화됨 | Progent의 초기 정책·승인, PAuth의 self-contained signed task, FORGE의 사용자 지정 Datalog 정책 모두 정답 정책/승인 경계에 의존한다([Progent §§3, 9](https://arxiv.org/html/2504.11703), [PAuth §§II–III](https://arxiv.org/pdf/2603.17170v2), [FORGE §2.3](https://arxiv.org/html/2602.16708)). 모호하면 인간 확인·정형 target 작성이 기존 해법이다. **질문:** 자동 번역의 오류를 독립 사용자 oracle이 없는 조건에서 어느 정도 검출할 수 있는가? |
| 출처 인증과 **내용 진실성**이 구별됨 | ROPE/PACT는 origin·인자 역할을 보고, PAuth는 권위 서버의 signed value를 사용한다. 출처가 진짜여도 그 내용이 사용자의 실제 선택과 일치한다는 결론은 별도다([ROPE §6](https://arxiv.org/pdf/2608.27496v2), [PAuth §III-A](https://arxiv.org/pdf/2603.17170v2)). **질문:** 승인된 문서가 공격자 쓰기 가능할 때 어떤 추가 권위·확인 절차가 필요한가? |
| 관측·정책 표현·집행 경계가 실제 효과를 덮음 | FORGE의 join point, ActPlane의 kernel event, OpenShell의 proxy, CTA/EffectBound의 provider sink가 보는 사실은 다르다([FORGE §7.1](https://arxiv.org/html/2602.16708), [ActPlane §3](https://arxiv.org/html/2606.25189), [EffectBound §II](https://arxiv.org/html/2609.02866)). **질문:** 특정 업무의 모든 effect-equivalent 경로와 최신 상태를 기존 계층의 조합으로 충분히 매개할 수 있는가? |
| 위임·철회 상태의 보존과 서비스 쪽 최종 확인 | caller 인증, origin grant, hop별 축소, queue/callback, provider effect는 각기 다른 속성이다([Donno et al. §§II–V](https://arxiv.org/html/2611.07050), [Authorization Revocation §§2–5](https://arxiv.org/html/2609.21284)). **질문:** 실제 비트리·영속·비동기 MAS에서 각 경계의 증거와 fence가 모두 충실한지 확인한 문헌이 있는가? |

## 이번 조사에서 새로 확인한 사실과 최종 판정

**기존 비교표에서 특히 수정해야 할 해석**은 다음과 같다. (1) Progent의 최신 확인 판본은 [arXiv:2504.11703v3](https://arxiv.org/html/2504.11703)이며 제목이 바뀌었고 갱신 확대의 SMT 검사·사용자 승인 경계가 있다(§§4.3, 6). (2) PAuth [v2 §V](https://arxiv.org/pdf/2603.17170v2)의 `off-task blocked`는 사용자 확인 단계 발동이고, 원래 AgentDojo 요청 29/100은 확인 없이는 허용되지 않았다. (3) ROPE의 청구서 위임 문제에는 [SPILLWAY v3 §§2–5](https://arxiv.org/pdf/2611.07222v3), PACT, PAuth, CXI라는 **조건이 다른** 반박이 존재한다. (4) FORGE의 [Appendix H.3](https://arxiv.org/html/2602.16708), NGAC-IR의 [§5.3](https://arxiv.org/html/2611.26941), AutoCedar의 [§V-D](https://arxiv.org/html/2607.03656)는 형식 검사 또는 번역 검사 뒤에도 의미 오류가 남은 **D 사례**다. (5) tool wrapper 밖의 경로는 ActPlane/OpenShell/AgentBound로, provider 안의 늦은 효과는 CTA/EffectBound/Authorization Revocation과 native API로 **이미 부분 대응**한다. 최신 프리프린트의 수치와 학회 판본의 수치를 혼합하지 않았다.

**최종 질문에 대한 답.** 문헌상 충분히 해결됐다고 보기 어려운 구체 조건은 **① 자연어 승인에서 정형 정책의 올바른 목표를 만드는 과정, ② 공격자 쓰기 가능 자료에 사용자가 민감 대상을 위임한 경우의 값 선택, ③ 장기 승인·다중 agent 위임·provider commit 사이에서 필요한 사실과 현재 효과를 끝까지 결속하는 과정**이다. 이 판단은 위의 D 사례와 A/B 제한에 근거하지만, 세 조건 각각에 **이미 강한 부분 해법과 전통적 대안**이 있다. 그래서 현 판정은 모두 **`PARTIALLY_RESOLVED`**이며, “기존 방법으로도 해결되지 않는 독립적인 새 Research Need”라는 더 강한 결론은 **`UNVERIFIED`**다. 특히 독립적으로 올바른 target·authoritative 값·완전한 service-side 매개와 원자 조건부 API를 제공하면 많은 사례가 해결된다. 이들 대안을 **같은 사용자 승인·위협 모델·정상 업무**에서 대조해도 남는 실패를 아직 확인하지 못했다. `OPEN_WITH_EVIDENCE`로 확정한 새 범용 문제는 이번 조사에서 없다.

다음 문헌 확인에 필요한 최소 조건은 문제별로 다르다. 정책 의미에는 독립 사용자 승인 target과 허용 정상 trace, 위임 값에는 동일한 attacker-controlled field와 별도 authoritative source 여부, 장기 위임·효과에는 동일한 승인을 보존한 채 코드/의존성/대상 버전·queue 상태만 바꾼 실제 provider trace가 필요하다. 이때 **정보가 없는지, 정책 언어에 표현할 수 없는지, 집행점이 없는지, 오래된 판단인지**를 분리해야 한다. 신규 프레임워크·공통 테스트베드·재현 실험은 이번 조사 범위에 넣지 않았다.

**접근 제한.** [Ghost Approvals](https://doi.org/10.1145/3847352.3848101), [ContractGuard](https://doi.org/10.1145/3830454.3846789), [LEASH](https://doi.org/10.1145/3847352.3848103), [Authorization-Preserving Context Lifecycles](https://doi.org/10.2139/ssrn.7580538)의 본문은 접근하지 못했다. 메타데이터·초록만으로 메커니즘이나 해결 관계를 확정하지 않았다. 조사에서 찾지 못한 연구가 존재하지 않는다는 뜻도 아니다.
