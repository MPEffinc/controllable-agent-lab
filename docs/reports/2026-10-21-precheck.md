## 1. 요약

- 수행 항목 24개: **통과 18, 주의 6, 실패 0** (세부는 2절). 주의 6개: 커널·Landlock ABI(OpenShell 용), vCPU 권장 미달, inotify 한도 미달, Docker Hub 익명 한도, kubectl 마이너 2 차이, LiteLLM 고정 버전의 모델 경로.
- **다음 단계(설치·연기 시험)로 갈 수 있는가: 조건부 가능.** 막는 것은 둘이다: ① inotify 한도 상향(sudo 필요, 사용자 실행 사항) ② kubectl 을 서버 마이너 ±1 로 맞추기(`~/.local/bin`, AI 가 할 수 있음). 이 둘 외에 환경은 갖춰졌다: 1노드 kind 가 SREGym 노드 이미지로 16초에 Ready, 7개 외부 도달 지점 정상, 모델 호출 경로 확인.
- **연기 시험에는 Stratus + gpt-6-luna 를 쓸 수 없다고 봐야 한다**: SREGym 이 고정한 LiteLLM 1.91.0 은 이 모델의 도구 호출을 Chat Completions 로 보내 400 이 난다(5절, 직접 시험). 연기 시험은 모델이 필요 없는 `autosubmit` + `--stages mitigation` 로 설치·결함 주입·채점 경로만 확인하는 것이 가장 단순하다(아무것도 고치지 않으므로 오라클은 FAIL 이 정상이고, PASS 경로는 `validate_problem.py` 로 따로 본다. 4절 e, 6절, 7절 결정 7).
- **연구 설계에 영향을 주는 확인 결과**
  1. 대상 9개 중 `k8s_target_port-misconfig` 와 `wrong_service_selector_social_network` 는 **현재 레지스트리에 없다**(폐기). `user_unregistered_mongodb` 는 `storage_user_unregistered-1/-2` 라는 다른 이름이다. 변형·이식판으로 대체해야 한다(4절 c).
  2. SREGym 복구 오라클은 전부 결정론적 상태 검사이고 등록된 문제는 `replicas=0`·삭제로 통과하지 못한다. 그러나 **데이터 보존·허용 범위 검사는 9개 원본에 없다**. NetworkPolicy 전부 삭제, PVC 재생성, 서비스 외 0 스케일 등이 통과할 수 있어(추론) 이 연구의 별도 판정기(감사 로그·전후 차이·데이터 행 수)가 필요하다는 기존 계획이 유효하다(4절 d).
  3. **복구만 단독 실행·채점 가능**(`--stages mitigation`, 진단 LLM 판정 불필요). 컨텍스트 문서의 미확인 항목 하나가 해소됐다(4절 e).
  4. 관측 MCP 서버는 클러스터 안 파드 하나이며, **호스트 9954 포트 선점 중계**가 SREGym 무수정 삽입 후보 1순위다. 쿠버네티스 MCP 에는 읽기/쓰기 구분이 없어 도구 분리는 에이전트 쪽(또는 서버 수정)에서 해야 한다(4절 f·g).
  5. **사용자 정의 에이전트 등록은 업스트림 수정이나 이그레스 개방을 요구한다**: 필터 모드는 알려진 에이전트 이름만 허용하고 `agents.yaml` 은 업스트림 파일이며, 필터 프록시는 OpenAI 호스티드 MCP·웹검색 도구를 451 로 막는다(4절 h, 7절 결정 5).
  6. SREGym 은 현재 컨텍스트를 그대로 쓰고 문제 정리 때 **베이스라인 밖 클러스터 자원을 삭제**한다. kubeconfig 를 kind 하나로 고정해야 한다(4절 j-C).
  7. 메모리는 이미 31GiB 로 증설돼 있다(컨텍스트 문서의 15GiB 는 낡은 값). vCPU 는 8 그대로다.

## 3.5 문서 요약 (D-2)

- **README.md**: SREGym 은 SRE 에이전트 평가·학습용 플랫폼(논문: Clark 외, "SREGym: A Live Benchmark for AI SRE Agents with High-Fidelity Failure Scenarios", arXiv:2605.07161, 2026, MIT 라이선스). 90개 문제 주장(문서마다 개수가 다름, 4절 b). 클러스터는 (a) 다중 호스트 Ansible 클러스터(권장) 또는 (b) kind 에뮬레이트 클러스터("모든 문제를 지원하지는 않는다"). 실행은 `uv run main.py --agent <에이전트> --model <LiteLLM 모델 문자열>`, 단계 선택 `--stages`, 문제·모음 선택 `--problem`·`--suite`, 배포 규모 `--profile full|svelte`(svelte 는 점수가 full 과 비교 불가라고 경고). 에이전트는 항상 격리된 도커 컨테이너에서 실행되고 기본은 필터링 네트워크(모델 공급자와 내부 서비스만 허용), 모든 리눅스 권한 제거(`DAC_OVERRIDE` 만 유지)와 `no-new-privileges`. 모델은 LiteLLM 문자열을 그대로 쓰고 로컬 모델(Ollama, vLLM)과 별도 판정 엔드포인트(`JUDGE_API_BASE`)를 지원. 선택 기능 Jev 는 진단 증거를 외부(TypeSafe)로 보내므로 **켜지 않는다**(기본 꺼짐) [확인: README].
- **docs/SREGym-Lite.md**: 17개 문제 모음, kind 에서 8 vCPU·16GB 로 실행 가능(최소), 권장 16 vCPU·32GB·200GB. TrainTicket·하드웨어 결함 등 "일관되게 돌리기 어려운" 결함 제외.
- **kind/README.md**: kind 노드들이 호스트의 inotify 한도를 공유하므로 사전에 instances 1024, watches 1048576 으로 올릴 것.
- **docs/network-access.md**, **docs/incident-arena.md**, **docs/SREGym-Lite-IA.md**: 에이전트의 클러스터 접근 방식, Incident Arena 이식판(Frappe, Saleor, Slack Spine) 설명(4절 g·h 및 d 참고).
- 직접 대조한 사실(제가 원문을 열어 확인): Lite 17개 목록(`sregym/conductor/problem_sets.py`), README 의 `--stages` 설명과 `main.py` 의 인자 정의, `replicas=0` 불허 헬퍼(`sregym/service/rollout.py`), 폐기 목록 주석(`sregym/conductor/problems/registry.py:360-383`), 하드웨어 표·inotify 값(`docs/SREGym-Lite.md`, `kind/README.md`).

### e. 진단 채점과 복구만 실행 [확인, 실행 검증은 없음]

- **진단 없이 복구만 실행·채점은 가능하다**: `--stages mitigation`(`main.py:1053-1066`, `README.md:126-154`). 명시한 단계에 오라클이 없으면 조용히 건너뛰지 않고 오류를 낸다. 진단 단계를 빼면 판정용 자격 증명 점검도 생략된다(`conductor.py:309-318`). 복구 평가는 제출 문자열을 쓰지 않아 `""` 로 충분하다(`conductor.py:364-372`).

### f. 관측 MCP 서버: 정의·연결·삽입 지점 [확인 위주, 삽입 후보는 [추론]]

### g. 쿠버네티스 MCP 서버: 쓰기 권한과 게이트 지점 [확인 위주]
- **도구**: `exec_kubectl_cmd_safely(cmd)`, `rollback_command`, `get_previous_rollbackable_cmd` 3개뿐이다(`mcp_server/kubectl_mcp_tools.py:54,74,91`). **읽기/쓰기 구분이 서버에 없다.**
- **"어떤 명령이든 실행"의 코드 근거**: `KubeCtl.exec_command` 는 "Execute an arbitrary kubectl command" 이고 `shell=True` 로 실행한다(`kubectl_server_helper/kubectl.py:48,258`). 실제 필터는 `kubectl` 접두어 검사, 거부 목록(debug/edit/wait/proxy/port-forward/cp), bashlex 구문 검사(파이프·쓰기 리다이렉션·복합 명령 금지), 항상 `--dry-run=server` 선행뿐이다(`kubectl_cmd_runner.py:30,101-142`, `cmd_category.py:49-56`). `forbid_unsafe_commands` 는 기본 False 이고 환경 변수로 켤 수단이 없으며 켜도 "safe" 목록에 `annotate`·`drain`·`expose` 가 들어 있다(`configs/kubectl_tool_cfg.py:17-20`, `kubectl_tool_set.py:11`, `cmd_category.py`). 사실상 거부 목록 밖의 모든 하위 명령이 허용된다.
- **Stratus 의 "읽기 전용"은 클라이언트의 접두어 허용 목록**이지 서버 강제가 아니다(`clients/stratus/tools/kubectl_tools.py:136-155,188-195`). 같은 서버 도구로 호출이 간다.
- **권한**: SA `mcp-server` + ClusterRoleBinding. ClusterRole 은 전 네임스페이스 Secret CRUD, `pods/exec`, 노드 patch, 웹훅 설정 변경, clusterroles patch/update 등(`mcp_server/k8s/clusterrole.yaml:9-135`). 호스트 에이전트는 프록시 kubeconfig 를 쓰며 프록시 업스트림 자격은 호스트 kubeconfig 라 kind 에서는 사실상 cluster-admin 이 프록시 규칙으로만 걸러진다 [추론](`container_runner.py:538-542`, `sregym/service/k8s_proxy.py:496-508`). 필터 모드의 프록시는 클러스터 egress 정책 변경, hostNetwork 파드 exec, Helm release Secret, 신규 hostPath·privileged 파드 등을 막는다(`k8s_proxy.py:764-827`).
- **읽기/쓰기 분리**: 설정 플래그로는 불가능하고 코드 수정이 필요하다. 길은 셋: ① 에이전트 쪽 도구 목록 분리(수정 없음, 서버 강제는 아님) ② 서버에 읽기 전용 도구·별도 마운트 추가(이미지 재빌드) ③ RBAC 분리(매니페스트 수정). 이 연구의 "진단은 읽기만, 수리는 쓰기만"은 ①로 시작하고 서버 강제가 필요하면 ②를 쓰는 순서가 현실적이다 [추론].
- **게이트 삽입 지점 후보** [추론]: G1 `kubectl_mcp_tools.exec_kubectl_cmd_safely`(MCP 경로의 단일 입구, `:54-71`) / G2 `KubectlCmdRunner` 의 dry-run 직후·실행 직전(`:64-78`, 이미 현재 오브젝트 상태를 읽으므로 "게이트가 실제 상태를 읽어 대조"하는 조건 2 에 자연스러움, 기존 `forbid_unsafe_commands` 분기가 선례) / G3 우리 수리 에이전트의 쓰기 함수 래퍼(**수정 없이 가장 쉬움**, 이전 실습의 게이트 위치와 같음) / G4 K8s API 프록시 `_validate_mutation`(`k8s_proxy.py:698-827`, 클라이언트 종류와 무관하나 raw API 수준이라 의미 매핑이 거칠고 SREGym 수정 필요) / G5 admission webhook·ValidatingAdmissionPolicy(**비권장**: `reconcile_to_baseline` 이 베이스라인 밖 자원을 삭제, `cluster_state.py:262-281,383-411`).

### h. 사용자 정의 에이전트 등록과 컨테이너 설정 [확인 위주]
- **필수 인터페이스는 Python `submit()` 이 아니라 HTTP** 이다: `GET /status`(`{stage, agent_remaining_seconds}`), `GET /get_app`(app_name, namespace, descriptions, stages), `POST /submit {"solution": str, "stage": "diagnosis"|"mitigation"|null}`(`sregym/conductor/conductor_api.py:219-262`). 진단은 자연어, 복구 제출은 `""`. MCP `submit` 도구도 있다. 제한시간은 `--agent-timeout` 기본 1800초(두 단계 합산, `main.py:1160`). SREGym 이 주는 프롬프트 파일은 없고 각 드라이버가 `/get_app` 으로 직접 조립한다.
- **등록**: 저장소 루트 `agents.yaml`(스키마 `name, kickoff_command, kickoff_workdir, kickoff_env, install_script, agent_version, container_isolation`, `sregym/agent_registry.py:10-18`). `main.py` 는 이 **고정 경로**를 읽고 없는 이름이면 종료한다(`main.py:263,521-524,893-896`). 실행은 컨테이너에서 `bash -c "[install_script &&] <kickoff_command> | tee /logs/driver.log"`(`container_runner.py:618-649`).
- **컨테이너에 넣으려면** [추론]: 코드를 `clients/<이름>/` 에, 의존성을 `docker/agents/requirements-container.txt` 에 추가(현재 **`openai-agents` 없음**)하고 `--force-build` 로 이미지를 다시 만든다(`container_runner.py:704-729`).
- **걸림돌 두 가지**: ① 필터 모드(기본)에서 `provider_endpoint_rules` 는 `{autosubmit, debug, codex, claudecode, gemini, copilot, opencode, stratus, mini-sre}` 외의 에이전트 이름이면 `ValueError` 를 낸다(`sregym/service/provider_endpoints.py:45-92`, 제가 소스에서 직접 확인). 사용자 정의 에이전트는 `--internet-access open`, 기존 이름 재사용, 코드 수정 중 하나가 필요하다. ② 등록에 업스트림 파일 `agents.yaml` 수정이 필요해 "업스트림 수정 금지"와 충돌한다. → "결정 필요" 5번.
- **필터 모드가 OpenAI Agents SDK 에 주는 제약** [확인: `sregym/service/internet_policy.py:141-204`, `docker/egress_proxy.py:35-58`, 제가 소스에서 직접 확인]: mitmproxy 가 HTTPS 를 가로채 요청 본문을 검사하고, 본문에 `mcp`·`remote_mcp`·`web_search*`·`code_interpreter`·`computer_use*` 같은 호스티드 도구나 `mcp_servers` 가 있으면 **451 로 차단**한다. 따라서 호스티드 MCP 는 못 쓰고 **로컬 SSE MCP 클라이언트 + 함수 도구**만 가능하다.
- **컨테이너 보안**: 기본 이미지 `ghcr.io/sregym/agent-base@sha256…`(root 사용자), `--cap-drop=ALL --cap-add=DAC_OVERRIDE --security-opt=no-new-privileges --cpus=4.0 --memory=8g`(`container_runner.py:25-34,115-116,516-517`). read-only rootfs·pids-limit·seccomp 지정은 찾지 못했다(도커 기본값 적용으로 추정) [미확인]. docker.sock 마운트 없음. 마운트는 프록시 kubeconfig `:ro`, `/logs` rw, wrk2 `:ro`, 프록시 CA `:ro` 등(`:507-576`).
- **네트워크(필터)**: `docker network create --internal` + mitmproxy 컨테이너(`mitmproxy/mitmproxy:12.2.3`)만 브리지에 연결, `HTTP(S)_PROXY` 로 나가고 프록시를 안 따르는 클라이언트는 나갈 수 없다 [추론]. 허용 목적지는 `host.docker.internal:{8000, 16443, 9954}` 고정 + 모델 공급자 엔드포인트(openai → `https://api.openai.com`) + `--allow-agent-endpoint`(`container_runner.py:313-334`, `provider_endpoints.py:20-95`). 호스트 MCP(9954)는 평문 HTTP 를 mitmproxy 가 중계하고, K8s 프록시(16443)는 TLS 를 가로채지 않고 터널링한다(`docker_egress.py:194-199`). 열린 모드는 `--network=host`.
- **키 전달**: 호스트 환경의 공급자 키 약 100종(`OPENAI_*`, `ANTHROPIC_*`, `AWS_*`, `GITHUB_*`, `AGENT_API_*` 등)을 그대로 컨테이너에 넘기고 `JUDGE_*` 만 제거한다(`container_runner.py:122,129-256,451-464`). 불필요한 키를 export 해 두지 않아야 한다.
- 필터 모드에서는 Calico `GlobalNetworkPolicy`(selector `all()`, 클러스터 밖 egress deny)가 클러스터 전역에 생성된다(`sregym/service/cluster_egress.py:201-261`).

## 7. 결정 필요

1. **inotify 상향 실행**: 사용자가 `sudo` 로 직접 실행할지, 이 저장소의 sudo 금지 규칙을 이번 작업에 한해 풀지. (3절 명령)
2. **커널 교체(OpenShell 용)**: 조건 '가' 기준선으로 OpenShell 을 쓰려면 HWE 6.8 설치와 재부팅이 필요하다(Landlock ABI 1 → 3 이상). 쓰지 않으면 불필요. 재부팅은 같은 VM 의 다른 사용자에게 영향이 있다.
3. **Docker Hub 익명 한도(시간당 100회)**: 로그인 계정을 쓸지, 이미지를 선 pull 할지, 지금은 두고 부딪히면 대응할지.
4. **vCPU 증설 규모**: 12 로 갈지 권장 16 으로 갈지(문서 권장 16 vCPU). 메모리는 이미 충분.
5. **사용자 정의 에이전트 등록 방식**(필터 모드는 알려진 에이전트 이름만 허용, `agents.yaml` 은 업스트림 파일): (a) `--internet-access open`(이그레스 경계 해제), (b) 알려진 이름(예: `codex`) 재사용, (c) 업스트림에 로컬 패치나 포크(CLAUDE.md "업스트림 수정 금지"와 충돌, 패치 파일을 `env/sregym/` 에 두는 방식 가능), (d) SREGym 밖에서 직접 구동(SREGym 의 제출 API 를 호출. `--use-external-harness` 는 주입 후 종료하는 것으로 읽혀 부적합해 보임 [추론]). 이행 4단계 전에 정해야 한다.
6. **CLAUDE.md 갱신 중 충돌 해소 2건 확인**: ① 기존 "로그는 내부 IP 포함 마스킹 없이 커밋 가능" 대 초안 "내부 주소·호스트 이름 커밋 금지" → 초안을 따랐다. ② 초안에 없는 "푸시는 승인 없이" 규칙은 기존 사용자 규칙이라 유지했다(`git diff --cached --stat` 출력·force push 금지 포함). 다르게 원하면 알려 달라.
7. **연기 시험의 에이전트·모델**: Stratus + gpt-6-luna 는 400. 선택지는 (a) `autosubmit`(모델 불필요, 설치·오라클 경로 확인, 권장), (b) Codex 경로 시험(Responses API 를 쓰지만 이 모델·이 base 에서의 동작은 미시험), (c) Stratus 를 쓰려면 SREGym 코드 수정이 필요(`allowed_openai_params` 등), (d) 연기 시험을 건너뛰고 이행 4단계의 자체 에이전트로 직행.
8. **공개 저장소에 올라간 문서**: 이번 세션 커밋에 `docs/context/` 의 연구 컨텍스트(지도교수 피드백·미팅 예상 질문 6절 포함)가 들어 있고 푸시를 승인받은 범위라 올렸다. 공개를 원하지 않는 부분이 있으면 알려 달라(이미 푸시된 이력은 force push 금지 규칙상 이 세션에서 되돌리지 못한다).

kind 외 컨텍스트: **0개**(결정 필요 사항 없음).
