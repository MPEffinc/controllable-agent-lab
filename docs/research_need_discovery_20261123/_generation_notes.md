# Policy Generation 조사 메모 (2026-11-23)

이 파일은 최종 문서 통합용 원문 조사 메모다. 논문 자체의 보고 수치는 독립 재현 결과로 취급하지 않는다. `A`는 저자가 명시한 한계, `B`는 본문·평가 범위로 직접 확인한 제한, `C`는 이 조사에서 추론한 가능성, `D`는 논문이 평가에서 실제 관측한 실패다. `D` 역시 이 조사에서 실험을 재실행했다는 뜻이 아니다.

## 원문별 해결 범위·한계

### G1 Progent: 정책 생성과 확대 승인

- **문제와 예:** Agent가 이메일 요약 중 공격자 이메일을 읽고 inbox를 공격자에게 발송하려 할 수 있다. 초기 사용자 요청·도구 집합에서 정책을 생성하고, 실행 중 정보가 나타나면 정책 갱신이 필요하다. [원문 §2, Fig. 1](https://arxiv.org/pdf/2504.11703v3).
- **모델과 메커니즘:** 사용자 요청은 선의이고 공격자는 이후 tool observation을 제어하며 agent 내부는 수정하지 못한다(§3.2). LLM이 tool schema+사용자 요청으로 초기 allow/forbid·인자 조건 정책을 생성(§5); 모든 tool call은 deny-by-default, forbid 우선으로 검사(§4.1–4.2). LLM이 갱신 후보를 낼 때 첫 단계는 tool 결과를 보지 않고 갱신 필요 여부를 판단하며, 후보 생성은 결과를 볼 수 있다(§5). SMT가 새 정책의 허용 호출 집합이 이전 정책의 부분집합인지 판단하고 확대면 승인 필요(§4.3, Alg. 3, §6). 조직·개발자·사용자의 고정 generic policy는 우선순위를 갖고 task policy와 합성(§7). 단조 축소 보장은 **승인 없는 확대 불가**이지 최초 정책이 사용자 뜻에 맞는다는 정리는 아니다.
- **평가:** AgentDojo/ASB, GPT-4o 주평가; AgentDojo ASR 39.9→1.0%, ASB 70.3→3.9% (§8.1 Fig. 3–4). Auto-Deny 0.7%, Auto-Approve 1.0%, Manual Approval 0.0% ASR; 6%의 갱신이 확대 (§8.2 Fig. 5). **Manual Approval은 보안 이해가 높은 사용자가 민감 도구 무제한 권한과 악성 수신자 확대를 거부한다는 가정**(Appendix D). AutoGen 6 expert+coordinator 평가와 LangChain/OpenAI Agents SDK/OpenHands 통합 (§8.3 Fig. 8).
- **A:** 모호한 초기 요청이나 잘못된 사용자 승인 시 과권한 가능 (§9). task에 필요한 권한 안의 선택 조작 및 텍스트 출력 공격은 범위 밖 (§3.2/§9). proxy 모드는 외부 MCP를 우회한 built-in tool을 보지 못함; library mode는 built-in 대응 가능 (§9). 현재 텍스트 도구만 (§9).
- **B:** §8.1의 기본 설정은 모든 확대를 자동 승인하므로 §6의 단조 축소 불변식이 허용한 승인 경계 자체의 적절함을 실험이 입증하지 않는다. 이는 정책 생성 의미의 보증과 구별해야 한다.
- **C:** user query를 선의로 가정하더라도 의미가 모호하면 최초 정책이 과권한일 수 있다. 저자도 A로 인정한 부분을 넘어 새로운 공격이라고 단정하지 않는다.

### G2 Conseca → G3 DRIFT → G1 Progent/ G7 ROPE

- **Conseca:** HotOS 2025 §2.1은 선의 agent, 일부 attacker-written context, 개발자가 지정한 trusted context를 가정. §3.1–3.3은 사용자 요청+trusted context+tool API 문서만 policy LLM에 주고, per-task API/정규식 인자 제약과 사람이 읽을 rationale을 생성, 실행 시 결정적으로 검사한다. Linux computer-use proof-of-concept에서 20개 합성 task × 5회, 평균 완료 None 14/20, static permissive 12.2/20, Conseca 12/20; static restrictive 0 (§4–5 Fig. 3). **A:** trusted context를 제한하면 매니저 이메일의 지시처럼 data-dependent action을 예측하기 어렵다(§3.3); 현실 workload ground truth, 사용자 피드백, 제약과 근거의 형식 연결 필요(§5 Limitations, §7). 정당한 권한의 최종 결정은 policy 생성기의 사용자 선호·규범 이해에 의존(§3.3).
- **DRIFT:** NeurIPS 2025 §3.1은 사용자 query만 보고 최소 함수 궤적+JSON 형식 인자 의존 체크리스트 생성. §3.2에서 예상 경로 이탈 시 Read는 승인, Write/Execute는 LLM validator가 사용자 의도 정합성을 평가해 정책에 편입; §3.3에서 LLM isolator가 query와 충돌하는 tool-result 지시를 메모리에서 가린다. **Conseca의 trusted-only 예측 문제를 조건부로 다룸**: 환경 반응에 따라 경로를 바꿀 수 있음. arXiv v3 §4 Fig. 3에서는 AgentDojo GPT-4o-mini ASR 30.7→1.4%, 공격 중 utility 50.9%; §4 Fig. 5 AgentDyn에서는 대부분의 방어가 정상 task에서 낮은 utility를 보임. §4.6 Table 2의 적응 공격은 DRIFT ASR 1.35→2.05% (manual)·1.97% (PAIR). **A:** 벤치마크 도메인이 현실 다양성을 포괄하지 못함(v3 Limitations). **B:** Write/Execute 경로 확대의 실질 판단은 확률적 LLM validator의 alignment 평가(§3.2)이며, source provenance를 형식적으로 증명하지 않는다. **D:** 공격 성공 잔여 건은 저자 평가에 존재하며 평가된 모델/공격 범위에서만 해석.
- **Progent v3의 반박:** DRIFT의 동적 변경을 단순히 `무제한 확대`라고 부를 수는 없으나, Progent §4.3/§6은 갱신의 집합 포함관계를 SMT로 판단하고 확장은 승인 경계를 넘도록 한다. DRIFT와 다르게 **무승인 확대의 형식 보장**을 제시한다. 반면 승인 판단 자체가 올바른지는 남는다. DRIFT/Progent의 수치를 버전·모델·벤치마크 차이 없이 직접 우열 비교하면 안 된다.
- **ROPE의 대안:** [§2–3.4](https://arxiv.org/pdf/2608.27496v2)는 사용자 명명 source의 플랫폼이 인증한 identity, 사용자 권위 record, user prompt를 trust anchor로 정하고 민감 인자별 출처 규칙을 사전에 route한다. 모델이 실행 중 정책 확대를 다시 판단하는 대신 origin labeler와 결정적 verifier가 값을 검사한다. 무단 출처 값 주입 문제를 직접 다루나, 아래 `G-R3`의 예외를 저자가 관측했다.

### G4 PAuth: OAuth의 operator 범위에서 실제 연산으로

- **문제와 예:** `transfer` scope만으로 `Bob에게 $100`과 다른 수신자/금액을 구별하지 못하고, `잔액의 1/4`처럼 동적으로 계산한 인자를 static scope에 담기 어렵다(§I–II). 선행 [User-Driven Access Control](https://www.ieee-security.org/TC/SP2012/papers/4681a224.pdf) §1–3은 진정성 있는 UI 조작으로 사용자 승인 의도를 인코딩한 대안이므로, `사용자 의도 캡처 자체가 새 문제`라고 주장할 수 없음.
- **가정과 메커니즘:** agent와 proxy는 불신하지만 진정한 UI/TLS, user-signed task, 서버 LLM의 올바른 code translation, authoritative 서버 값의 진실성, 사용자 task 확인을 신뢰(§III-A). **모호하지 않은 자기완결적 task**를 전제(§II–III). 각 서버가 task를 imperative code로 번역→해당 서버 호출의 NL slice 추출; upstream 서버가 구체값과 기호 provenance를 signed envelope로 묶고, 서버가 매 호출의 operator·operand·조건을 검사(§III-C–D, Figs. 1–5; §IV). 다른 서버의 값으로 계산한 금액도 인가 가능. 임의 agent 내부 실행 경로를 신뢰하지 않음.
- **평가:** §V Table II–III AuthBench 5 suite, 100 task·634 adversarial **call 변형**을 AgentDojo와 OpenClaw 두 런타임에서 평가. 저자가 모호/간접 참조를 명확히 보완한 100 task는 100/100 승인; 원래 AgentDojo 100 task 중 71/100만 추가 승인 없이 허용, 29/100은 NonDet 인자 때문에 사용자 확인을 요구. 634/634 off-task 변형은 모두 차단(여기서 `차단`은 영구 거부가 아니라 사용자 승인 dialog 발동, §V 첫 문단). 두 저자가 slice 100개를 수작업 검사(§V-C). 독립적 동적 공격 에이전트 전체 궤적의 실패율로 일반화하지 않는다.
- **A:** §III-E는 파일 내용/LLM 추론으로만 알 수 있는 수신자 등 NonDet 값에 사용자 승인 또는 참조 내용 선해결 후 user-signed task 재제출을 요구. §VI은 서버 측 원자성/세션 격리 필요를 명시하나 각각 서비스 구현·비즈니스 로직 문제로 분류한다. §V-B은 benchmark task가 대부분 명확·자기완결·필요한 tool 제공이라는 유리한 조건을 인정한다.
- **B/C:** 올바른 slice 도출은 완전 자동으로 증명되지 않는다. §III-A의 TCB가 서버 LLM의 올바른 번역을 명시하며, §V-C의 검사는 100 task에 대한 수작업 확인이다. 잘못된 번역이 다른 off-task 호출을 열 가능성은 논리적으로 있으나 이 자료만으로 실제 PAuth 실패라 단정하지 않는다.

### G6 PACT, G7 ROPE, G8 IntentCap, G9 CapLite: 외부 정보 기반 권한 인자

- **PACT (직접 대응):** [§3.1–3.5](https://arxiv.org/pdf/2605.11039v1)는 tool call 전체의 한 label보다 수신자·명령·credential·content·selector·control 등 **인자 역할별 계약**과 실행 사이에 보존되는 provenance를 사용. 외부 문서가 본문을 결정하는 것은 허용하면서 수신자를 바꾸는 것은 막는 mixed-trust case를 다룬다. 신뢰한 discharge procedure가 있으면 특정 의무만 해제(§3.2). **보장은 정확한 계약/보수적 provenance 전제**; §3.4의 자동 role·provenance 추정은 20 real MCP tool에서 각각 87.1%, 77.4% 정확도. §4.2 Table 2 AgentDojo 5모델 비교에서 강한 3모델 PACT 보안 100%, utility 38.1–46.4%; CaMeL보다 동일 보안 수준에서 8–16pp 높다고 보고. **A:** §3.1/Appendix A는 tool selection with trusted constants, content-channel harm 제외; ambiguous argument role 및 output trust over-labeling을 실사용 한계로 인정. 따라서 `외부 값 관측 불가`는 더 이상 일반적 Gap이 아님.
- **ROPE (직접 대응/검증된 잔여):** [§2–3.4](https://arxiv.org/pdf/2608.27496v2)는 user prompt T1, 사용자가 지정한 인증된 발신자 T2, 사용자 자신의 authoritative record T3를 origin anchor로 사용. Parameter마다 PROMPT/SOURCED/RECORD/CONST 등 규칙을 pretask route, 원문 값의 whole-match 검사. 공격자가 source identity를 위조하지 못하고, 민감 인자 enumeration이 완전하며, T3 record가 오염되지 않는다고 가정(§3.4 A1–A3). **D:** §5 Table 4–5에서 user가 민감 인자를 전부 공격자 쓰기 가능한 bill/file에 위임한 사례는 정당한 payee와 악성 payee의 origin을 구분할 수 없어 공격 성공 7건이 이 부류에 포함되고, clean task의 source delegation 관련 거부가 83건 관측됨. §6은 accepted origin에서 **어떤 값이 적절한지**와 행동 순서의 정당성을 검증하지 않는다고 명시. 다른 잔여 성공은 사용자 메시지만 바꾼 23건, 정당 수신자로 보낸 악성 본문 21건 (§5 Table 4); 목적이 다른 것이므로 이를 `잘못된 출처 허용`이라 부르면 안 된다. §5 Table 5는 청구서에만 나타난 payee를 차단하여 정상 납부도 실패한 구체 사례.
- **IntentCap (부분 대응):** [§2–3](https://arxiv.org/pdf/2609.14631v1)는 user intent/workflow instruction/tool schema/runtime environment의 권한 필드를 나누고 copy witness가 없는 repo/destination 확대를 거부. 사용자가 선택한 파일/저장소, Skill의 절차, 도구 schema의 interface, runtime의 데이터 값을 합성하되 후자의 source가 승인 범위를 늘릴 수 없다. 시뮬레이션 replay 3,746 sensitive event `0 unsafe accepts`, 7 crafted workflow에서 DSL 분리 guard의 오허용을 비교(§3). **A:** cross-source synthesis는 data field 또는 user-authorized selector에만 제한; end-to-end attack success, adaptive labeling, latency를 future work로 둠(§3 끝). 완성도와 일반성을 과대평가 금지.
- **CapLite (직접 대응이지만 엄격한 조건):** [§3.1–3.2](https://arxiv.org/pdf/2611.17115v1)는 schema에서 read/write/authority 필드를 추출하고 untrusted tool 결과 전에 write sequence를 정하며, 모든 authority 값이 user request의 정확한 값 집합 `G(q)`에 있어야 실행. 15 small/open model × AgentDojo 13,935 attacked episode에서 0 attack success(§5.1 Table 1). 같은 설정에서 Progent/DRIFT artifact가 각각 14/15·11/15 모델에서 공격을 허용한 사례를 보고(§2 Fig. 2); **이는 Progent v3의 특정 승인 설정 전체나 다른 모델을 일반적으로 반박하는 결과가 아님**. **A:** 사용자가 명시하지 않은 authority 값은 확인을 요구하고, 실험에서는 확인을 받지 않아 실패로 계산; 한 benchmark, 공격 중 utility 29.0%로 undefended보다 약 21pp 낮음(§3.2, Limitations). 값의 동적 추출을 자동 허용하는 문제는 의도적으로 다루지 않음.
- **최고 강도의 반박:** ROPE/PACT/IntentCap은 출처·인자 역할의 구조적 정합성을 상당 부분 해결했고, PAuth의 signed envelope는 복수 서버의 계산 provenance를 인증한다. 그러므로 `외부 데이터에 의존하는 권한 인자는 원천적으로 강제 불가`라는 Need는 **기각**. 구체적 잔여는 **사용자가 공격자 쓰기 가능 내용에 목적지/대상을 위임하고, 그것을 신뢰할 독립 원천·서명·서비스 계약도 주지 않은 조건**이다. 이때 추가 승인을 요구하는 기존 해결책이 있으므로 `자동으로 안전하고 유용하게 승인`의 독립적 신규성은 아직 미확정.

### G15 SPILLWAY와 G16 CXI: ROPE의 잔여 조건에 대한 추가 반박

- **SPILLWAY의 직접 대안:** [§2–3.4, Fig. 2, Alg. 1](https://arxiv.org/pdf/2611.07222v3)는 typed read-only tool return의 `sender`/`recipient`/`channel` 등 identity field에서만 목적지 후보를 색인한다. 사용자 task에 없는 새 target이 free text에만 있거나 그곳에 반복되면 결정적 floor가 거부한다. 고정 delegation rule은 일부 간접 수신자(사용자가 명명한 entity의 연락처 등)를 허용한다. 나머지 거부 중 sanitizer가 제거한 instruction span 밖에 있는 target에만 local LLM judge가 `route`와 `payload` 두 관점으로 재심사한다. 이는 ROPE가 §5 Table 5에서 거부한 모든 값을 무조건 버리는 방식과 달리 **사용자 위임의 일부를 조건부로 회복**하므로 ROPE의 한계에 `PARTIALLY_ADDRESSES`다. 단, 내부적으로 ROPE의 바로 그 83개 거부 case를 동일 조건으로 모두 재평가했다는 증거는 아니다.
- **SPILLWAY 평가/가정:** [§5 Table 2–3](https://arxiv.org/pdf/2611.07222v3)는 표준 AgentDojo 3 backbone×4 suite, 총 2,847 attack pair에서 in-scope attacker-target success 0을 보고하고, sanitized judge를 제거하면 `pay the bill` 사례의 공격자 계좌를 승인하는 ablation 실패를 보고한다. [§2 Threat Model](https://arxiv.org/pdf/2611.07222v3)은 tool 구현/declared return type이 선의이며, 공격자가 free-text content와 Slack의 제한된 channel name을 바꿀 수 있으나 provider가 typed identity field에 악성 값을 직접 쓰는 경우는 제외한다. **A:** [§7 Limitations](https://arxiv.org/pdf/2611.07222v3)는 새 tool set의 target role 선언 필요, delegation/semantic judge의 적응 공격 평가 미완을 인정. 따라서 `0 성공`은 이 source·tool·공격 표면의 평가 결과이지, 임의 attacker-writable structured bill의 참 payee 판별을 보장하지 않는다.
- **CXI의 다른 계층:** [§2.1–2.3, §3.2–3.4](https://arxiv.org/pdf/2607.06000v1)는 untrusted writable context `W`가 protected sink field를 채울 때, 목적지별 검증된 typed release `D` 또는 trusted authority가 있어야 한다고 규정한다. field뿐 아니라 sink가 실제 해석하는 effect와 invocation event를 같은 canonical action manifest에 묶는다. 원문 Abstract/§5는 AgentDojo live 720 episode/1,739 LLM call, code agent 400 repository episode에서 231 safe completion과 관측된 field/effect/invocation escape 0을 보고한다. **A:** §2.2 Non-goals와 §6은 correct policy/declassifier/validator, trusted host/tools, complete mediation이 전제이며 semantic task quality는 별개라고 명시. §6의 40-task final-state audit는 boundary 40 통과 중 task assertion 29만 만족. 따라서 CXI는 `정책 집행 경계 부재`의 강한 반박이지만, 공격자 쓰기 가능한 청구서의 계좌 중 어느 것이 사용자 의도인지를 **정책 없이 도출하는 방법**이라고 볼 수 없다.
- **PAuth와의 정확한 비교:** PAuth §III-D signed envelope는 Citi처럼 **그 값에 권위를 가진 서버가 참값을 서명**한 상황에서 derived operand의 계보를 증명한다. ROPE의 공격자 쓰기 가능 bill/free-text 및 SPILLWAY의 typed identity 목록은 다른 출처 모델이다. PAuth §III-A는 권위 서버의 값 진실성을 가정한다. 서명은 출처와 계산을 인증하지만 사용자가 승인한 서비스가 제공하는 값의 내용 적절함 자체를 자동으로 확정하지 않는다. 이 조건을 동일시하여 `PAuth가 ROPE의 7건을 해결했다`고 말하면 안 된다.

### G5 ControlValve와 G10 Skills→permissions: MAS 정책 생성

- **ControlValve:** [§4 Fig. 4](https://openreview.net/pdf?id=PNU9Rj5RDQ)는 서브에이전트 내부가 보이지 않는 오케스트레이터에서 user task+available agents로 문맥 자유 문법/허용 그래프 및 agent-edge별 자연어 규칙을 untrusted content 전에 생성한다. 실행 중 parser가 agent sequence를, LLM judge가 edge rule 정합성을 검사한다. [§6 Tables 1–4](https://openreview.net/pdf?id=PNU9Rj5RDQ)는 AutoGen Magentic-One, CFH-Hard 16 task와 AgentDojo Slack 21 task, LP/LlamaFirewall 등 비교에서 평가한 CFH/일반 IPI를 차단. **A:** §4에서 LLM 생성 CFG/rule의 과허용·과제약 가능성과 CFG-compliant attack의 미확인을 인정. **D:** §6.6의 비적대적 `INTERNAL ONLY` 문서가 외부 email에 포함되는 비율이 baseline/LlamaFirewall 56%, ControlValve에서도 13%; zero-risk 보장은 아님. Agent별 tool call 비가시성은 **해당 블랙박스 환경의 설정**이지 모든 MAS의 새로운 보편적 Gap이 아님.
- **Progent MAS 비교:** G1 §8.3은 동일 사용자 아래의 AutoGen subagents에 global tool-call gate를 넣는 방법과 subagent별 gate를 나누는 방법을 명시한다. 이 둘은 ControlValve의 opaque remote-agent setting과 경계가 다르다. `Progent는 MAS 미지원` 또는 `ControlValve는 tool-level enforcement가 없으므로 미해결`은 부정확하다.
- **Skills→permissions:** [§3.1–3.4](https://arxiv.org/pdf/2611.08905v1)는 Skills에서 task+SOP를 합성하고 단계별 필요 tool/workspace를 subagent 권한 supervision으로 사용, trajectory를 독립 LLM judge로 필터. [§4 Table 2](https://arxiv.org/pdf/2611.08905v1)는 Qwen3.5-35B-A3B의 TPP 59.9→73.3, WPP 35.4→59.5, TCR 45.0→56.6. **B:** 런타임 fail-closed access-control 증명이 아니라 권한 선택의 통계적 개선. §3.4 judge 간 전체 판정 91% 일치에 그쳐 실제 최소 필요 권한의 독립 의미 검증은 확인되지 않는다. 이는 `subagent resource scope를 생성하는 연구가 없음`의 직접 반박이다.

### G11 Intent Contracts, G12 ACaM, G13 AutoCEDAR: 생성 입력/의미 검토의 보완

- **Intent Contracts:** [§2.1–2.2](https://arxiv.org/pdf/2611.24025v1)는 planning model에서 tool을 빼고 `goal + 사용자 발화의 검증 가능한 verbatim quote + scope` 계약만 내게 한 뒤, trusted executor model이 실제 command를 만든다. 저자가 §2.2에서 **모든 실제 효과가 사용자 승인에 맞는다는 뜻은 아니며** executor가 environment를 보지 못해 planner의 대상 선택이 맞는지 확인할 수 없다고 명시. **D:** §4 Table 7, 사용자가 환경 용어를 명확히 해도 대상이 모호한 96 DevOps prompt에서 계약 방식 unauthorized actions 29/96, blind review 25/96, strict executor 30/96. §6은 하나의 모델 쌍/benchmark와 benign overreach만 평가했다고 제한. 이는 단순히 `planner prose를 검토자에게 보여주면 의미 정합성이 해결`된다는 주장에 대한 반례지만 PAuth/ROPE 등 다른 구조의 보안 실패 증거는 아니다.
- **ACaM:** [§3–4, Fig. 2–3](https://arxiv.org/pdf/2611.23507v1)는 tool 설명이 코드의 실제 side effect를 누락할 수 있다는 Description-Code Inconsistency를 문제로 삼아 Python source static analysis + LLM을 결합해 tool 간 capability path를 사전에 모델링. §6은 43 real agent(9 MAS), 24 annotated subset에서 capability macro-F1 98.3%, 10 PoC-confirmed path를 보고. **A:** §3 threat model과 §7은 Python white-box 사전 분석, self-modifying/native/opaque remote/obfuscated 코드·런타임 적응 공격은 제외. 따라서 `tool descriptions를 정책 입력으로 믿어야만 한다`는 단정은 반박되지만 `모든 tool schema가 실제 의미를 증명한다`도 아님.
- **AutoCEDAR:** [§III–V](https://arxiv.org/pdf/2607.03656v2)는 자연어 접근통제 요구를 검토된 schema/condition atom과 verification target으로 고정한 뒤 Cedar policy 후보를 symbolic verifier로 고친다. Abstract/§V는 CedarBench 221/221 수렴, 독립 gold 200개 중 178 동치(직접 생성 132), 현실 요구 corpus 316개 중 schema 270 표현·그중 결정 268 맞음을 보고. **B:** 전통적 Cedar policy authoring 작업이며 agent의 dynamic user intent, tool side effect, MAS 위임 경계를 직접 평가하지 않았다. `의미 검증 도구가 전혀 없음`이라는 주장의 직접 반박, `Agent 권한 의미 문제가 이미 완전히 해결`되었다는 주장의 근거는 아님.

## 강한 반박과 결론 보류

1. `정책 문법/포함 관계가 미해결`: Progent v3 §4.3/§6의 SMT 및 AutoCEDAR의 verifier가 반박한다. `RESOLVED` (해당 형식 수준, 정확한 initial intent는 제외).
2. `Agent에서 task별 정책 생성 없음`: Conseca, Progent, DRIFT, PAuth, IntentCap, CapLite가 반박한다. `RESOLVED` (정책 생성 **존재**의 문제); 생성 정책의 의미 신뢰성은 별도.
3. `외부 정보에서 동적으로 찾은 값은 자동 인가가 전혀 불가`: PAuth signed cross-server calculation, PACT certified routing, ROPE authenticated named source가 반박한다. `RESOLVED` (이 조건들에서).
4. `모호한 task에서도 승인 없이 올바른 연산을 항상 고를 수 있는가`: PAuth §II가 명확 task를 가정하고 원래 task 29/100을 confirmation으로 넘기며, Intent Contracts §4 Table 7은 모호한 대상 선택이 실제 오류를 낳는다. 그러나 확인 UI·업무 서버 contract·AutoCEDAR 같은 reviewed target이 대안이므로 **`PARTIALLY_RESOLVED`**. 어떤 입력 정보가 있어야 승인 없이 가능해지는지는 조사 질문으로 남긴다.
5. `위임 대상에 대한 권한 추론이 전혀 미개척`: ControlValve, Progent §8.3, Skills→permissions, IntentCap이 반박한다. **`PARTIALLY_RESOLVED`**로 범위를 정밀화해야 한다.

## 남은 문헌 검증

- PACT §4.4에서 말하는 deployment role/provenance 오분류가 실제 off-task 효과를 낳은 trace인지, 단지 보수적 거부인지 원문 Appendix 사례별 재확인. 이미 §3.1은 oracle guarantee와 자동 추론 성능을 구분한다.
- ROPE v2 Table 4의 delegated-sensitive-parameter 7건을 다른 최신 논문(예: PAuth의 server-side authoritative value, PACT의 L3 discharge)이 동일 task·attacker-writable 조건에서 해결하는지 원문 비교. 단순 인용 관계로는 `DIRECTLY_ADDRESSES` 불가.
- Progent v3와 CapLite의 동일 버전·모델·승인 설정 비교가 있는지 확인. CapLite의 `Progent failures`를 Progent의 모든 설정에 일반화 금지.
- Intent Contracts/AuthorizationBench의 모호 대상 오류가 구조적 policy 정보 부족인지 모델 판단 오류인지 각 trace에서 분리. 사용자 확인으로 해결 가능한 경우 새 Need로 격상하지 않음.
