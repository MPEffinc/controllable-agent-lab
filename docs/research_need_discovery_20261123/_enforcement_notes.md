## 문제 → 대응 → 잔여 조건의 연결

### C1. Tool dispatch 우회와 더 낮은 집행 경계

1. **P-E1**: Progent/FORGE가 tool call·일부 HTTP join point에서 정책을 잘 집행해도, uninstrumented subprocess, raw socket, custom client가 실행 경계를 지나지 않을 수 있다. FORGE는 raw sockets/direct stdio와 intra-method concurrency의 event-graph 누락을 직접 한계로 적는다 (**A**). [FORGE §7.1](https://arxiv.org/html/2602.16708).
2. **E02 → E03 `PARTIALLY_ADDRESSES`**: ActPlane은 kernel hook에서 process-tree의 syscall을 관측하므로 `exec git` 같은 tool wrapper를 우회한 효과도 해당 file/connect/write hook에서는 보인다. 다만 파일 내용·API 의미·표현되지 않은 kernel effect는 범위 밖이다 (**A/B**). [ActPlane §2.3, §3.1–3.4](https://arxiv.org/html/2606.25189).
3. **E02 → E16/E11 `ALTERNATIVE_APPROACH`**: OpenShell은 sandbox의 Landlock/프록시, AgentBound E11은 MCP server Docker network/filesystem boundary를 쓴다. OS/네트워크/실서비스 요청이 이 경계를 지나면 tool-only 누락은 **이미 존재하는 경계 계층**으로 줄일 수 있다. 단, OpenShell `audit`는 차단이 아니고, L7 rule 누락·허용 서비스 내부의 악성 인자는 별도 정책·검사가 필요하다. [OpenShell overview/best practices](https://docs.nvidia.com/openshell/v0.1.9/security/best-practices), [AgentBound §5](https://arxiv.org/html/2510.21236).
4. **판정**: `PARTIALLY_RESOLVED`. 특정 tool guard의 미관측 경로를 일반적인 미해결 인가 취약점으로 승격하면 안 된다. 더 좁은 질문은 *의도한 business effect를 판정하기 위한 인자가 OS/network 계층에 충분히 있는가, API/서비스 계층을 함께 강제했는가*다. 이는 연구자 추론 **C**이며 실제 통합 배포의 실패 **D**는 여기서 확인하지 못했다.

### C2. 출처·정보흐름 집행에서 agent 간 승격

1. **P-E2**: 단일 CaMeL/IFC 해석기 안에서 출처를 보호해도, orchestrator가 tool/DB의 untrusted output을 child의 trusted instruction field로 재포장할 수 있다. Multi-CaMeL의 SQL-agent 예제는 이 composition 실패를 재현한다 (**D**, 해당 예제·설정). [Multi-CaMeL §III](https://arxiv.org/html/2610.05640).
2. **E04 `DIRECTLY_ADDRESSES`**: `message`/`variables` 분리, provenance와 capabilities 전파, interpreter 경계 유지로 tree-shaped fresh child 호출에 대해 이를 집행한다. Table III의 공격 성공률 0은 이 benchmark 설정에 한정된다. [§IV–V](https://arxiv.org/html/2610.05640).
3. **E04 → E06 `PARTIALLY_ADDRESSES`/`ALTERNATIVE_APPROACH`**: Multi-CaMeL이 약한 CFI만 목표로 하고 implicit flow·retry-loop 문제를 인정하는 한편, LLMbda는 TIPNI calculus와 Lean interpreter로 그 종류의 흐름을 더 강하게 다룬다. [Multi-CaMeL §VI-B](https://arxiv.org/html/2610.05640), [LLMbda §1–5](https://arxiv.org/html/2602.20064). FIDES도 label·quarantined query라는 다른 IFC 경로를 제공한다. [FIDES §3–5](https://arxiv.org/html/2505.23643).
4. **잔여**: Multi-CaMeL은 multiple parents, persistent child state, async queue, peer cycle을 스스로 미래 과제로 둔다 (**A**). 이 조건에서 공격이 이미 성공했다고 한 것은 아니며, CONTINUITY/E08/E09는 다른 계층에서 handoff·sink·carrier를 각각 다룬다. **판정 `PARTIALLY_RESOLVED`**; 일반 그래프 MAS에서 정확한 통합 보호의 실증 상태는 `UNVERIFIED`.

### C3. Agent에서 허용한 행위가 provider effect까지 같은 의미로 유지되는가

1. **P-E3**: tool-call 시점 판단 후 대상 버전·payload·현재 권한이 바뀌거나, provider 내부에서 queued effect가 뒤늦게 commit될 수 있다. EffectBound의 GitHub MCP `read reviewed head → merge` 경로와 Kafka 4.3.1 in-flight ProduceRequest는 각각 **D** 사례다. [EffectBound §II, §V-B–C](https://arxiv.org/html/2609.02866).
2. **E07 `PARTIALLY_ADDRESSES`**: CONTINUITY는 effect finality sink에서 exact permit, provenance, current revocation 등을 재검사하는 보안 계약을 제안한다. 그러나 평가 대상은 deterministic synthetic reference system이고, 실제 provider route/validator 정당성은 전제다 (**A/B**). [§5–8, §12](https://arxiv.org/html/2609.05269).
3. **E09 `DIRECTLY_ADDRESSES`**: EffectBound는 의도한 effect의 frontier와 provider가 제공하는 **관측·제어 인터페이스**로 안전성+정상 완료 가능성을 판정한다. GitHub native API의 commit SHA precondition은 MCP 경로의 경쟁을 제거하는 실제 대안이다. Kafka에는 old-instance fence를 추가하여 명시된 경로를 시험했다. `MCP API에는 불가능`을 `GitHub에서 불가능`으로 확대하면 안 된다. [§III-C, §V](https://arxiv.org/html/2609.02866).
4. **고전적 반박**: linearization point/atomic precondition이라는 원리는 새롭지 않다. [Herlihy & Wing, *Linearizability*, TOPLAS 1990, §1](https://www.cs.columbia.edu/~wing/publications/HerlihyWing90.pdf). 적절한 provider API를 골라 정확한 정책을 구현할 수 있다면 agent 특유의 open need로 보지 않는다. **판정 `PARTIALLY_RESOLVED`**: 특정 interface 결핍은 입증됐지만 일반적 집행 불가능성은 아니다. 실제 provider 경로와 요구되는 정상 완료를 고정해야 판단 가능하다.

### C4. 비동기 위임과 철회: 신규 인증 거절, 잔여 효과, root quiescence는 다른 목표

1. **P-E4**: 프로세스 kill·작업 cancel·credential revoke 뒤에도 이미 수용된 callback/queue/provider 작업이 effect를 낼 수 있다. E08의 provider-free 17-case suite에서 cancellation-only·root cut-only 경로가 늦은 effect를 허용한다 (**D**, 이 참조 환경). [Authorization Revocation §2 Table 1, §8](https://arxiv.org/html/2609.21284).
2. **E14 `PARTIALLY_ADDRESSES`**: HBHC는 descendant credential의 신규 인증을 bounded freshness로 막는다. 이 성질은 이미 provider에 들어간 작업을 막거나 되돌리는 성질과 다르다. [HBHC §3–4, §7](https://arxiv.org/html/2605.20704).
3. **E07/E08/E09 `ALTERNATIVE_APPROACH` 및 `PARTIALLY_ADDRESSES`**: CONTINUITY는 개별 effect의 finality permit, Authorization Revocation은 root cut 이후 manifested sink 전체의 carrier accounting+fence+certificate, EffectBound는 각 provider 경계에서 *해당 애플리케이션 정책이 거부할 효과 경로*의 closure를 각각 정의한다. 이들은 목표 술어가 달라 직접 확장 계보로 묶을 수 없다. E08의 §9도 이 구분을 밝힌다. [E07 §3–6](https://arxiv.org/html/2609.05269), [E08 §9–10](https://arxiv.org/html/2609.21284), [E09 §II](https://arxiv.org/html/2609.02866).
4. **전제 검사**: E08의 sink manifest·durable fence·정확한 transfer accounting·bounded time이 충족되지 않으면 certificate는 `INDETERMINATE`여야 한다 (**A**). E09의 finite contract도 provider-wide path completeness를 증명하지 않는다 (**A**). 따라서 `비동기 철회는 아무도 다루지 않았다`는 틀리다. `실제 특정 provider의 모든 경로에 배치·검증됐는가`는 현재 `UNVERIFIED`이며 곧바로 새로운 보편적 취약점은 아니다.

### C5. 다중 agent 권한 전파에서 현재 caller와 origin을 혼동하는 문제

1. **P-E5**: A2A `A0→A1→A2`에서 A2가 A1을 인증해도 A0의 승인 범위를 증명한 것은 아니다. E10은 current caller, inherited authority, per-hop request authentication, independent replay를 분리해 시험한다. [§I–III, Table I](https://arxiv.org/html/2611.07050).
2. **E10의 잔여 D**: path verifier에 scope inclusion 검사가 없어 isolated widening 1/15가 통과했고, authorized intermediary가 공유 HMAC 키로 origin authority를 바꾼 evidence를 만들 수 있었다. 후자는 E10의 full application check까지 통과한다. 정확한 범위는 **shared-HMAC trust model의 원천 보존 실패**이며 모든 서명 기반 delegation 방식의 실패가 아니다. [§V-A–B](https://arxiv.org/html/2611.07050).
3. **대안 검색 경로**: E10 Table I 및 §I가 직접 비교한 South et al. authenticated delegation, SAGA(NDSS 2026), HDP, AIP/APS, OAuth [RFC 8693](https://www.rfc-editor.org/rfc/rfc8693), structured RAR [RFC 9396](https://www.rfc-editor.org/rfc/rfc9396), DPoP [RFC 9449](https://www.rfc-editor.org/rfc/rfc9449), HTTP Message Signatures [RFC 9421](https://www.rfc-editor.org/rfc/rfc9421)은 각각 다른 부분을 다룬다. E10의 요약표만으로 어느 하나가 **A2A에서 전 조건을 해결**한다고 확정하지 않는다. [E10 Table I](https://arxiv.org/html/2611.07050).
4. **판정**: E10 자체 제한은 `D`로 확정. *기존 방법을 조합해도 origin-verifiable attenuation이 불가능*하다는 연구 Need는 `UNVERIFIED`. 특히 signed origin grant + per-hop narrowing + downstream verification이 실제 A2A 프로파일에서 구현·평가됐는지 원문 대조가 필요하다.

### C6. Per-action 정책과 전체 실행·관계적 정책

1. **P-E6**: 개별 행위가 허용이어도 흐름 전체에서 동일한 consent/purpose 정책이 지켜지는 것은 아니다. E15는 single-trace CAF와 서로 다른 실행을 비교해야 하는 2-safety purpose 속성을 구분한다. 정리의 범위는 저자 모델과 `false-alarm-free per-trace monitor`에 한정된다. [E15 §III–V](https://arxiv.org/html/2610.27620).
2. **E02/E07 `PARTIALLY_ADDRESSES`**: FORGE의 event history Datalog 및 CONTINUITY의 transition/finality contract는 단일 행위 이상을 본다. 따라서 `모든 agent monitor가 단일 tool-call만 본다`는 오해다. 하지만 관계적 두 실행을 비교하는 목적 속성에 대해 E15의 single-trace 불가능성 주장은 그대로 구별해야 한다. [FORGE §3–4](https://arxiv.org/html/2602.16708), [CONTINUITY §3–6](https://arxiv.org/html/2609.05269).
3. **고전적 반박**: multi-trace monitoring/secure multi-execution은 기존 연구 대상이다. [Coenen et al., *Runtime Enforcement of Hyperproperties*, arXiv:2203.04146, §3–5](https://arxiv.org/abs/2203.04146). E15 스스로 이 계보를 인정하고, 6개 guardrail은 profile 조사이지 전체 실행 재현이 아니다. [E15 §VIII–IX](https://arxiv.org/html/2610.27620). **판정**: per-trace 집행의 수학적 불가능성은 확인됐지만 곧 `OPEN_WITH_EVIDENCE`인 새로운 연구 Need는 아니다. 고전적 relational 집행을 특정 agent 목적 정책·정상 업무에 적용했을 때의 잔여 문제는 `UNVERIFIED`; 해당 조건을 먼저 고정해야 한다.

## 정확성·신규성 검토를 위한 교차 경계

- **정책이 옳다는 전제**: FORGE §2.3은 사용자가 Datalog 정책을 의도대로 지정했다고 가정한다. ActPlane §5.1에서 컴파일 성공은 의미 정합성을 보이지 않는다. CONTINUITY §12는 trusted root와 semantic validator의 진위를 증명하지 않는다. 이는 집행 실패와 정책 의미 실패를 분리해야 한다는 강한 근거다. [FORGE §2.3](https://arxiv.org/html/2602.16708), [ActPlane §5.1](https://arxiv.org/html/2606.25189), [CONTINUITY §12](https://arxiv.org/html/2609.05269).
- **출처와 내용**: provenance label, 서명, root grant가 **누가 어느 경로로 냈는지**를 검증해도 원문 데이터의 진실성이나 사용자 의도의 정확한 해석을 자동으로 증명하지 않는다. CONTINUITY는 이를 explicit A limitation으로 쓴다. [§3.5, §12](https://arxiv.org/html/2609.05269).
- **SkillScope라는 반박**: agent skill의 task-conditioned 과권한 여부에는 이미 CCS 2026 연구가 있다. instruction/code graph, authorization·task necessity 판단, guard/split repair를 사용하고, 평가에서 triggered overprivileged action-in-task 472→54로 보고한다. 판단에 LLM과 counterfactual replay가 관여하므로 deterministic complete mediation과 동일시하면 안 된다. [SkillScope §2–6](https://arxiv.org/html/2605.05868). 남은 문제를 `집행점 부재`로 쓰기 전에 **정확한 정책을 누가 정하는가**와 **허용된 skill 내부 효과가 어디까지 보이는가**를 나눠야 한다.
- **동명 오류**: AgentBound E11의 Docker MCP boundary와 E12의 signed constitution/authorization/site action contract는 별개다. E12는 §8·§10.2에서 실험·artifact를 미래 계획으로 적고, §3.2에서 prompt injection을 범위 밖으로 둔다. 기여를 합산하거나 E12를 검증된 집행 성능으로 인용하면 안 된다. [E11 원문](https://arxiv.org/html/2510.21236), [E12 §3.2, §8, §10.2](https://arxiv.org/html/2606.30970).
