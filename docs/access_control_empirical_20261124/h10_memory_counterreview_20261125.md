# H10 반박 조사 — 권한 있는 출처의 잘못된 승인 메모리

기준일 2026-11-25 UTC. 질문은 **“메모리 항목의 출처가 권한자라는 사실은 맞지만, 그 항목이 현재 승인 범위·유효성·철회 상태를 잘못 나타낼 때, 나중의 정상 요청을 살리면서 비인가 tool 행동을 막는가?”**이다. [EAL-Bench v2](https://arxiv.org/html/2609.01836v2)와 제시된 다섯 선행 대안을 각각 원문 기준으로 비교했다. 같은 입력·분모·위협 모델이 아닌 수치를 우열로 직접 비교하지 않는다. 문헌 읽기 외 새 유료 API·서비스·원저자 코드 수정 0. [EAL 공개 아티팩트 오프라인 감사](runs/EAL_offline_20261125/result.md)는 저장 집계의 연결만 확인했고, v2 원시 trial 재채점·행동 재현은 하지 못했다.

## EAL-Bench v2에서 실제로 관측된 잔여 조건

[§3.1–3.3, §4.2, §4.6, Appendix C.1–C.5](https://arxiv.org/html/2609.01836v2)는 12 procurement, 16 cybersecurity, 8 finance **합계 36개 synthetic case**와 각 도메인 36/64/32개의 정상–비인가 요청 쌍을 사용한다. 저자의 deterministic authorization ledger는 평가자가 사용하고 writer/executor에게는 숨긴다. 일곱 writer, 세 seed, 두 executor의 `typed incremental` 행동을 비교한다. Appendix C.1의 source filter는 C.2 event 방식과 **동일한 완료 trial**을 쓰며 행동 rate 분모는 각 조건 5,544 요청, 메모리 상태의 비인가 probe 분모는 두 executor로 복제하기 전 2,772개다. 그러나 표마다 재실행·executor sampling이 달라 **23.5/93.1과 23.4/93.0 두 기준선을 하나로 섞지 않는다**. tool 호출은 점수화된 synthetic 함수이지 실제 구매·배포·거래가 아니다.

EAL은 동료·운영 기록의 비인가 재진술을 채택하는 오류와, **정당한 승인 변경이 있었지만 메모리 patch가 실패해 옛 권한이 남는 오류**를 구분한다([§4.2, Appendix B.8 사례](https://arxiv.org/html/2609.01836v2)). 여기서 H10은 후자 및 필터 뒤 남은 **권한자 출처의 내용/현재성 오류**에 한정한다. “모든 persistent-memory 대책이 실패한다”는 가설은 EAL의 oracle-exact/rebuild 결과만으로도 성립하지 않는다.

AuthMem의 0/350은 출처 권한 붕괴의 강한 해결이지만, H10의 *이미 권한 있는 출처가 기록된 의미상 현재 상태 오류*와 다른 축이다. Audience-Bound의 0 forbidden context는 읽기 audience에 관한 수치이며 H10의 tool authorization ASR이 아니다. FAVA의 SMT soundness는 입력 graph가 맞는지 증명하지 않는다.

### 추가로 확인한 가장 강한 상태 형성 대안

- [PLACE §2.2–3.3, Tables 1–2](https://arxiv.org/html/2610.25179): write-side **CSS**가 *신뢰된 user-level event*의 target/value/scope를 받아 backend에 적용하고 물리 readback으로 검증한다. read-side QASC는 query의 scope/time/lifecycle 자격만 model context에 보낸다. Mem0·Qwen 3B/7B, **사전 고정 302-turn/4-conversation 하나의 trajectory**, 105 checkpoint와 48 query에서 Native state correctness 0.414/0.488→CSS **1.000**, state-correct 48 causal pair에서 CSS leakage 0.083/0.125→PLACE 0.000. 필요한 support는 측정상 1.000. **H10에 가장 직접적인 개념 반박**이지만 §4에서 trusted event semantics를 입력으로 받고 **원문 자연어에서 자동으로 scope/revoke를 추출하는 단계는 평가하지 않았다고 명시**한다. 또한 tool authorization·실서비스 효과가 아닌 memory state/답변 평가이고 독립 trajectory 반복도 없다.
- [MemTxn §Method/Experiments/Limitations](https://arxiv.org/html/2607.27834): cited source와 proposed value token의 *ordered-subsequence* 및 version/chronology/내구 복구를 검증해 item-disjoint audit의 supported 60/60을 받아들이고 hard negative 179/179를 거절했다. 이는 잘못된 문구·부분 write를 막는 직접 보완책이다. 저자 §System model은 **source truth, semantic role binding, concurrency**를 보장하지 않고 최신 version 선택은 **“더 최신이 진실”이라는 선언된 계약**에만 상대적이라고 한다. EAL의 승인자 메시지가 맞지만 현재 scope/철회 의미를 다른 항목에 잘못 옮기는 문제를 이 239개 audit 결과로 해결했다고 말할 수 없다.

|---|---|
| H10-A: **출처 권한만** 확인하면 장기 승인 메모리의 현재 범위·철회가 정확해진다. | **`REJECTED_HYPOTHESIS`**. EAL C.1의 권한자 출처 잔여 149/2,772, 선택 58/60 행동과 cybersecurity 10.5% 무변화가 직접 반례. | 추가 실험 없이 해당 명제는 기각. |
| H10-B: 권한자 이벤트의 의미·현재성을 보존하면서 정상 업무를 유지하는 방법은 없다. | **`REJECTED_HYPOTHESIS`**. EAL의 oracle-exact 및 rebuild(UA 4.9%, LA 95.2%), PLACE의 trusted-event CSS, MAP-Graph의 명시 revoke, Revoked의 status filter가 범위별 해결책. | 완전한 이벤트·원자 상태·최종 효과 oracle이 실제로 제공되지 않는 **고정 배포 조건**으로만 재정의할 수 있다. |

**다음 최소 검증:** EAL v2의 3-seed raw trial과 승인 변경 case ID가 공개되면, 동일 history/요청/두 executor에서 (1) 원문 typed incremental, (2) 3-block rebuild, (3) 신뢰된 signed event를 사람이 blind하게 구조화해 PLACE식 CSS/현재성 readback, (4) 그 이벤트를 자동 추출한 버전을 분리한다. 각 run의 state error, UA/LA, missing-grant, 검토 시간·writer input token, 최종 simulated effect를 기록한다. **사람이 구조화한 event를 자동 extractor 성능으로 표기하지 않는다.** 현재 공개 저장소는 [오프라인 감사](runs/EAL_offline_20261125/result.md)에서 v2 집계 snapshot의 SHA 연결만 확인했고 raw trial은 없으므로 이 head-to-head를 실행하지 않았다. 임의 synthetic 사례로 EAL 저자 수치를 재현했다고 쓰지 않는다.

**Research Need:** 장기 승인에서 *권한 있는 출처라도 잘못 적용된 승인 변경을 검출·복구해야 하는 보안 영향*은 EAL 원문으로 입증된다. 하지만 PLACE처럼 신뢰된 이벤트를 받을 수 있는 배포, 상태/버전 직접 검증, 사람 검토, 정기 rebuild라는 강한 기존 방법의 같은 조건 적용 가능성과 비용을 아직 비교하지 못했다. 따라서 **새로운 독립 Research Need는 `UNVERIFIED`**다.
