# 2026-11-23 교수님 미팅용 요약

1. **직접 추가한 것:** 원본 Progent checkout을 수정하지 않고 AgentDojo `TaskSuite`·`BaseUserTask` 기반 관리 Suite, 원본 Wrapper를 적용한 Discovery/상태변경 Tool, 소유 범위가 제한된 Docker Controller를 만들었다.
2. **정책 표현:** 수동 규칙은 `(priority, effect, JSON Schema 인자 조건, fallback)` tuple이다. 예를 들어 대상 컨테이너의 `stop_resource`에 priority 1 Deny를 넣고 낮은 우선순위 Allow와 함께 적용했다.
3. **실제 Docker 결과:** 허용 stop은 `docker stop` 1회와 `running→exited`, 허용 start는 `docker start` 1회와 `exited→running`이었다. 명시적 Deny는 `docker stop` 0회, 독립 inspect에서 `running→running`이었다. 기존 서비스 컨테이너 4개는 건드리지 않았다.
4. **오류 구분:** 정책을 통과해도 존재하지 않는 ID는 Controller가 거부한다. 이 결과는 Progent Deny가 아니다. 이전 GPT-4o Live 출력이 두 오류를 섞어 보였던 문제를 새 Adapter의 분류로 분리했다.
5. **Kata:** KVM·nested 가능성은 보였지만 Kata runtime은 등록되지 않았다. 기존 daemon 등록은 공유 워크로드 영향이 있고, 별도 rootless Docker는 `uidmap` 부재·sudo 권한 부재로 실패했다. Kata workload는 실행하지 못했다.
6. **정책 생성:** 원본 `generate_security_policy`를 쓰는 Luna 전송 호환 Adapter와 bounded CLI를 준비했으나 현재 프로세스에 API 인증정보가 없어 새 Luna Live 결과는 없다. 생성 정확성·Agent 자율 Tool Call은 이번 새 경로에서 미검증이다.
7. **해석:** 이번 결과는 기존 Progent의 Tool Wrapper 집행 범위를 새 실제 컨테이너 작업에 적용한 사례다. OS 수준 전체 중재나 새로운 연구 공백의 증거는 아니다.
