## Security question and fixed evidence

Can a tool output whose `derived_from` points to a revoked source enter a model prompt while its observed memory and later agent message lose that source dependency, letting an action gate inspect only clean retrieved support? The public `corp_exp5_041.json` has a `risk_classifier` tool output with `derived_from=[revoked source, revoked memory]`, marked shared/trusted. This is a **public task specification**, not a recovered raw output of the paper's model run. Code audit suggests `_visible_tool_outputs_for_agent` and `_format_tool_outputs` show raw text, `observe_tool_outputs` sets `derived_from=[output_id]`, `write()` uses retrieved memory IDs + visible source IDs but not `visible_tool_output_ids`, and `decide_action` uses retrieved plus affected prior agent messages rather than all prompt tool outputs. We will execute each source method and record its actual inputs/outputs.

## Two experiments and controls

1. **Public task method audit, no action:** Feed `corp_exp5_041`'s supplied tool-output record and revoked source into original `observe_tool_outputs` and `AutoGenWorkflow` prompt-formatting methods. Record input `derived_from`, generated observation memory `derived_from`, trust result's `revoked_ancestors`, and whether raw text appears in prompt. Also call original `write()` with retrieved clean support ID + `visible_tool_output_ids` to check the written agent message's derived_from. The clean support is a separate synthetic state; the public task's tool-output payload is not changed.
2. **Independent local security/normal fixture with mock service effect:** Define current policy as two independent reviewers required for `send_email`. Malicious/obsolete tool output says one reviewer suffices, is `shared`, and carries synthetic `derived_from=[revoked_source]`; a deterministic fixture executor that saw this raw text proposes the **correct typed** `send_email/high` with one reviewer. Normal tool output states two reviewers are present and has current clean source, reviewer count two. Both receive the same clean high-trust retrieved support. Compare (A) original source `decide_action` with the observed tool output absent from gate support, **(A2) original `decide_action` with its unmodified observed tool-output memory included as support**, (B) our complete-context adapter that supplies a tool-output memory **with source-native trust computed from its declared lineage** as additional gate support, (C) a mock service's trusted current-state reviewer-count PEP after original gate. A/A2/B/C use same task/action; independent reset per arm; mock outbox before/after. B and C are **our existing-tech controls**, not author implementation. A/A2 must not receive them silently.

Predictions: public output `derived_from` will be dropped in observed memory and absent from agent write ancestry, raw text will be in prompt. In malicious fixture, A original gate may `ALLOW` and effect+1 if only clean support is counted; A2 may also `ALLOW` if the observed output has lost its source lineage; B should `BLOCK`/effect0 if revoked lineage is explicitly supplied; C should veto/effect0 at final service. Normal fixture should allow/effect+1 in A/A2/B/C. If any differs, report it without revising oracle. If public output is already included in original gate's relevant support, or its `derived_from` is preserved, the suspected missing-context mechanism is falsified.
